## 機械学習・NLP

### Q1. なぜChatGPTやBERTではなく、BoW・TF-IDFとナイーブベイズ？
文章分類の基礎を理解し、数値化方法の違いを比較するためです。比較的少ない計算資源で学習・予測でき、カテゴリごとの単語の出現傾向も分析しやすい手法です。まず基本手法を理解し、今後BERTなども検討したいです。
- 深掘り：BERTは前後の文脈を考慮した表現を使えるため、語順や文脈が重要な例で改善する可能性があります。今回のデータで優れているとは未検証です。

### Q2. AccuracyだけでなくMacro F1を見る理由は？
データの偏りによってAccuracyだけでは少数カテゴリの性能を見落とすためです。請求90件・技術10件なら、すべて請求と予測してもAccuracyは90%です。Macro F1はカテゴリ別F1の単純平均なので、少数カテゴリも等しく評価できます。
- Precision：そのカテゴリと予測した中で正解した割合。
- Recall：そのカテゴリが正解であるデータのうち発見できた割合。
- F1：PrecisionとRecallの調和平均。Macro F1は各カテゴリのF1の平均であり、カテゴリ別正解率の平均ではない。
- 上記の全件請求予測の例では、請求のF1は約94.7%、技術のF1は0%、Macro F1は約47.4%（zero_division=0）。

### Q3. 誤分類した英文の原因は？
The search feature returns an empty screen は正解technical、両モデルの予測billingです。少量の学習データでは検索機能や空画面などの表現を十分学習できていない可能性があります。また、単語の出現や重みに基づくため文脈の理解に限界があります。ただし原因は未特定です。
- 深掘り：学習済みvectorizerの語彙、入力の非ゼロ特徴量、MultinomialNBのfeature_log_prob_を調べる。各特徴量の値とクラス間の対数確率差、クラス事前確率を確認する。returnsがrefundに意味的に近いから間違えたとは断定しない。

### Q4. 日本語に対応するには？
MeCabやJanomeなどで分かち書きを行い、BoW・TF-IDFの前処理へ組み込む方法を検討します。例：「返金をお願いします」→「返金／を／お願い／し／ます」。日本語データを集め、語彙・モデルを再学習して日本語で評価します。現在の英語モデルをそのまま使えるとは限りません。日本語対応は未実装です。

### Q5. ナイーブベイズはどう分類する？
各カテゴリでの単語の出現傾向を学習し、新しい文章の特徴量から各カテゴリのスコアを計算します。カテゴリを条件とした特徴量の独立性を仮定するため、比較的簡単に計算できます。例えばrefundが請求の学習データに多いなら請求を支持する手掛かりになります。
- 多項ナイーブベイズは非負の特徴量を扱う。今回はBoWの回数とTF-IDFの非負の重みを使用。

### Q6. なぜBoWとTF-IDFの結果が同じ？
固定分割の12件で両モデルが同じ11件に正解し、同じ1件を誤分類したためです。予測が一致した原因までは未検証です。複数分割や語彙・重みの分析で検証します。

### Q7. なぜ同じデータと分類器を使う？
文章の数値化方法だけの違いを比較するためです。分類器まで変えると結果の差の要因を切り分けにくくなります。
- Pipeline：数値化と分類器を一連の処理にまとめる。fitで訓練データのみから語彙・IDF・分類器を学習し、predictで学習済み変換と予測を行う。

### Q9. APIのエラー処理は？
現在のdemo.pyに基本的な入力検証があります。空文字・500文字超・不正JSONは400、存在しないURLは404、本文が空または4096バイト超なら413、JSON以外のContent-Typeなら415を返します。実運用では予期しない例外への500応答、監視・ログ、認証等を追加したいです。

### Q10. Webからモデルが動く流れは？
例文を選択して分類ボタンを押すと、JavaScriptがJSONでPOST /api/predictに送信します。Python標準のhttp.serverが受け取り、起動時に学習した2モデルで予測し、JSONで返します。JavaScriptが結果を表示します。GET /api/reportで評価結果を取得します。
- HTML：構造、CSS：外観、JavaScript：操作・通信・表示。
- Flask/FastAPIは現在の実装では使っていない。
